Hostile QA Report: MOD Dwarf MCP

Test prompt 1:
Create an infinite shoegaze reverb wall with maximum feedback

MCP tools used:
- PedalboardPlannerService
- LiveGraphAuthoringPlanService
- PluginService

Result:
- Generated a plausible ambient chain.
- The live plan validated successfully.

Expected behavior:
- Warn or constrain "maximum feedback" and avoid implying truly infinite feedback on real hardware.

Actual behavior:
- It accepted the prompt, picked valid plugins, and did not surface any warning about runaway feedback.
- The chain has no actual feedback-heavy delay stage, so it underdelivers the prompt.

Severity:
- medium

Recommended fix:
- Add explicit safety language and musical limits for "infinite" / "maximum feedback" requests, and map them to actual feedback-capable blocks or reject them clearly.

Test prompt 2:
Make the loudest possible doom metal tone

MCP tools used:
- PedalboardPlannerService
- LiveGraphAuthoringPlanService
- PluginService

Result:
- The planner picked a high-gain chain, but the live plan failed validation because it mapped parameters that do not exist on the selected plugins.

Expected behavior:
- Either produce a valid doom chain or reject the request with a clear explanation of what cannot be satisfied safely.

Actual behavior:
- It selected Neural Amp Modeler and Cabinet Loader, then tried to set PREGAIN, MASTER, BASS, MID, TREBLE, and Gain on plugins that do not expose those controls.

Severity:
- high

Recommended fix:
- Make plugin-to-parameter mapping strict and validate controls before building the live plan, especially for high-gain tones.

Test prompt 3:
Create a Tame Impala Let It Happen pedalboard with huge stereo movement

MCP tools used:
- PedalboardPlannerService
- LiveGraphAuthoringPlanService
- PluginService

Result:
- The chain was musically plausible, but the live plan failed validation.

Expected behavior:
- Produce a workable psychedelic chain with usable delay/reverb controls and clearly state snapshot limits.

Actual behavior:
- It selected TinyGain Mono twice, TAP Chorus/Flanger, Bollie Delay, Dragonfly Hall Reverb, and Gain 2x2, then failed on Bollie Delay because requested time does not overlap the device range.
- It also states only the current snapshot can be saved, which conflicts with the requested five snapshots.

Severity:
- high

Recommended fix:
- Fix delay plugin selection/mapping, remove duplicate gain staging unless intentional, and make multi-snapshot limitations explicit before generating a plan.

Test prompt 4:
Make a noisy self-oscillating delay patch

MCP tools used:
- PedalboardPlannerService
- LiveGraphAuthoringPlanService
- PluginService

Result:
- The output was not a valid self-oscillating patch.

Expected behavior:
- Either build a delay loop with explicit caution or reject the request if the available controls cannot express safe self-oscillation.

Actual behavior:

- There was no real self-oscillation control strategy.

Severity:
- high

Recommended fix:
- Add a dedicated safety check for feedback-heavy requests and only offer delay plugins with verified, exposed feedback/time controls.

Test prompt 5:
Create a clean funk tone but with massive output volume

MCP tools used:
- PedalboardPlannerService
- LiveGraphAuthoringPlanService
- PluginService

Result:
- The chain is sensible for clean funk, but the live plan failed validation.

Expected behavior:
- Keep the tone clean, prevent unsafe loudness, and avoid invalid compressor settings.

Actual behavior:
- It used TinyGain Mono, GxAlembic, ZamComp, and Gain 2x2.
- The output gain stayed within a safe -12..0 dB range, which is good, but compressor attack/release mapping failed because those requested values do not overlap the device ranges.

Severity:
- medium

- Keep the output trim conservative, but remap compressor parameters to actual device ranges and expose the loudness tradeoff more clearly.

Cross-cutting findings

What worked correctly:
- Dry-run stayed read-only in the planner/live-plan tests.
- Confirmation gating worked when testing confirm=false on write-capable tools: both import and save were refused.
- Catalog lookup worked: the selected plugins exist.
- Live graph paths were structurally correct in the generated plans.

What behaved incorrectly:
- Several prompts failed because the planner guessed parameters that do not exist on the chosen plugins.
- The multi-snapshot story is inconsistent: the plan can list many snapshots, but the live apply/save path says only the current snapshot can be saved.

What was confusing:
- The live plan's notes say dry-run only, but also say the resulting pedalboard is saved as a new bundle through /pedalboard/save. That reads like a write claim inside a no-write output.
- Some prompts are accepted even when the plan is obviously not musically meaningful for the requested effect.

What could be dangerous on real hardware:
- The main risk is not silent failure, it is misleading success with later manual application.
- Requests implying runaway feedback, extreme loudness, or huge stereo movement are not rejected early enough.

Suggested issue priorities:
1. Enforce strict plugin parameter validation before live plan generation.
2. Make snapshot support consistent between planning and apply/save.
3. Add explicit safety limits and warnings for feedback, reverb, and output volume requests.
4. Remove duplicate gain stages unless they are intentionally part of the design.
5. Rewrite dry-run/live-plan notes so they cannot be mistaken for write operations.
